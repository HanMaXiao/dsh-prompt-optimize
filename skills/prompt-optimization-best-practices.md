# 提示词优化最佳实践

> 本 skill 由 `@local/dsh-prompt-optimize` 插件提供。基线正文是固定的；末尾「已积累的经验教训」段落由 `prompt_tune_learn` 工具不断追加，加载时请一并读完。

## 这个 skill 解决什么

用户常常「心里知道要干什么，但打出来的字不足以让 Agent 干对」。优化提示词不是把话说长，而是**把缺失的信息补成执行者能直接照做的形状**，并且**不编造任何用户没说的事实**。

它和「系统提示词文档」是两件不同的事：

| 场景 | 该用哪个 |
|------|---------|
| 一句话交办一个中小任务（改样式、修 bug、写个脚本） | **优化输入本身**：`prompt_tune_guide` / `prompt_tune`，然后直接开干 |
| 任务跨多个阶段、要交给**另一个新会话**执行、需要长期复用 | 先优化输入措辞，再走 `@local/dsh-prompt-mode` 的 `prompt_doc_write` 产出系统提示词文档 |
| 任务大且用户输入本身就很糙 | **先优化这次输入，再决定要不要出文档**——这是最主要的用法 |

判断依据只有一条：**交付物是「一段话」还是「一份能被反复读取的文档」**。

## 七块标准

一段专业的提示词应当七块齐全。缺哪块，执行者就只能在那里猜：

1. **角色** —— 谁在干（身份、专长、立场）。
2. **目标** —— 要拿到的**结果**，不是要做的动作。
3. **上下文与数据源** —— 去哪读事实：真实路径、规格、现状。
4. **交付物** —— 交出什么、什么形态、放在哪。
5. **硬性约束** —— 不允许做什么、边界在哪、什么时候必须先问。
6. **验收标准** —— 一条可判定的判据：跑什么命令、看什么输出算通过。
7. **输出格式** —— 回答怎么组织：先给什么、多长。

## 两个工具的用法

- **`prompt_tune_guide`** —— 先跑它。它不起模型、即时返回：给出七块的具备/缺失清单 + 一份按标准补全的改写。草稿只是「结构不全」时，这一步就够了，别浪费 token。
- **`prompt_tune`** —— 用词、逻辑、语气本身不到位时用它。它跑一次模型调用，返回**只有改写后的正文**，可直接替换用户输入或粘贴进新会话。

调用纪律：

- `draft` 传**用户的原话**，逐字，不要自己先清理、翻译或归纳——优化的前提是看清原始输入。
- 优化的是**提示词**，不是任务本身。除了这一次改写，不要顺手去执行提示词里描述的工作；用户没说「开始做」就先停。
- 模型返回的正文里如果出现 `<待确认>` 一类占位，原样保留并明确告诉用户「这几个值我不能替你编」。

## 硬性要求

- 用户没说的**事实**（路径、版本号、文件名、接口名、数字）一律不许编。缺失就写成明确的待确认项。
- 路径、命令、标识符、专有名词**原样保留**，不翻译、不改写大小写。
- 用用户草稿的语言。用户写中文就用中文，不要自动切英文。
- 保留草稿里的**全部**具体信息：一个路径、一个数字、一条约束都不能丢。
- 改写结果跟着内容走：草稿一句话，结果就不要写成一篇。
- 交付时给**可直接使用的正文**，不要贴对比表格、不要给多个候选版本。

## 交付形态

- 在会话里：把改写后的正文整段给出（它就是要被复制走的东西），再用不超过 3 行说明这次补了哪几块、有哪些待确认。
- 不要在回复里重复用户的原始草稿，除非用户在核对差异。

## 自迭代

每次出现「人工又修了一遍」「用户说优化得不对」「某类草稿反复处理不好」的情况，用 `prompt_tune_learn` 记一条：一句话说清**下次该怎么做**，并在 `evidence` 里留下当时的草稿与输出。教训会进入本 skill，下一个会话就能读到。
